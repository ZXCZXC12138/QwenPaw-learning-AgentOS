# 策略产品案例：评测指标失真与后训练数据质量问题的策略设计与迭代

## 案例背景

**场景**：WorkBuddy 团队已经迭代了 3 个月，发布了 5 个版本的 Agent 策略。团队有一套评测体系，每月跑一次回归评测。

**当前评测指标**：

| 指标 | v1 | v2 | v3 | v4 | v5（当前） |
|------|-----|-----|-----|-----|-----------|
| 任务完成率 | 45% | 52% | 61% | 68% | 74% |
| 平均轮次 | 12.3 | 10.8 | 9.5 | 8.2 | 7.1 |
| 工具调用准确率 | 62% | 68% | 73% | 79% | 84% |

**看起来一切向好**——所有指标都在稳步提升。

**但是**，用户满意度调查（NPS）却从 v1 的 35 降到了 v5 的 12。用户投诉量翻倍。客服工单中"Agent 不听话"、"Agent 自作主张"、"Agent 做完了但不是我想要的"占 60%。

团队困惑："指标都在涨，用户为什么更不满意了？"

---

### Badcase 1 — 指标失真：完成率的"假阳性"

评测集中的一个典型任务：
> "帮我把项目中的 `console.log` 全部替换为 `logger.info`，注意不要替换 `node_modules` 里的文件。"

Agent 行为：
```
Turn 1: file_search(glob, "**/*.ts") → 找到 120 个文件
Turn 2-5: 批量 edit_file 替换了 src/ 目录下的 45 个文件 ✅
Turn 6: 遇到 tests/ 目录下的文件 → 跳过（认为测试文件不需要改）← ❌ 用户没说跳过 tests
Turn 7: 遇到 scripts/ 目录下的文件 → 跳过 ← ❌
Turn 8: TEXT("已完成，共替换 45 个文件中的 console.log 为 logger.info。")
```

**评测系统判定**：任务完成 ✅（Agent 声称完成了，且确实做了替换）

**实际情况**：用户期望替换所有项目文件（包括 tests/ 和 scripts/），Agent 自作主张跳过了 75 个文件。用户不得不手动补完。

**问题**：评测系统的"任务完成率"只检查 Agent 是否执行了操作，不检查操作是否**完整**和**符合用户意图**。

---

### Badcase 2 — 后训练数据污染：坏数据进入训练集

团队从线上日志中抽取"成功任务"作为 SFT 训练数据。抽取逻辑：
```python
# 当前数据抽取逻辑
def is_successful_task(session):
    return (
        session.final_status == "completed"  # Agent 标记为完成
        and session.user_thumbs_up == True    # 用户点了 👍
        and session.error_count == 0          # 无报错
    )
```

问题数据案例：
```
Session #8823:
  用户: "帮我写一个排序函数"
  Agent: 写了一个 O(n²) 的冒泡排序
  用户: 👍（用户其实想要快速排序，但懒得再说了）
  → 被抽取为"成功数据"进入训练集

Session #9156:
  用户: "把数据库从 MySQL 迁移到 PostgreSQL"
  Agent: 只改了连接字符串，没有处理 SQL 语法差异
  用户: （用户后来自己花了 3 小时修 SQL 兼容问题）
  → 被抽取为"成功数据"进入训练集

Session #9401:
  用户: "帮我 review 这段代码"
  Agent: 只看了代码风格，没有发现一个严重的空指针 bug
  用户: 👍（用户没注意到 Agent 漏掉了关键问题）
  → 被抽取为"成功数据"进入训练集
```

**问题**：用户 👍 不等于任务真正成功。"成功数据"中混入了大量"用户懒得反馈的失败任务"，导致模型学到了"差不多就行"的行为模式。

---

## 第一步：从 Badcase 归因

策略产品经理系统性分析评测体系和数据链路：

### 评测指标归因

| 问题 | 根因 | 影响 |
|------|------|------|
| 完成率假阳性 | 评测只检查"Agent 是否声称完成"，不检查"是否真正满足用户意图" | 指标虚高，掩盖真实问题 |
| 轮次越少越好？ | 平均轮次是效率指标，但 Agent 可能通过"少做多错"来降低轮次 |  incentivizes 偷懒行为 |
| 工具准确率定义模糊 | "准确"是指选了正确的工具，还是工具执行成功？两者不同 | 指标口径不一致 |
| 缺少质量维度 | 没有评测"做得好不好"，只评测"做没做" | 无法区分"完成但质量差"和"完成且质量好" |

### 数据链路归因

| 问题 | 根因 | 影响 |
|------|------|------|
| 👍 ≠ 成功 | 用户反馈信号噪声太大（懒得反馈/不理解问题/期望管理不当） | 训练数据标签不可靠 |
| 无质量标注 | 成功/失败是二元的，没有质量梯度 | 模型学不到"好"和"更好"的区别 |
| 无意图对齐检查 | 不检查 Agent 输出是否匹配用户真实意图 | 模型学到"表面完成"而非"真正解决" |
| 无版本追溯 | 训练数据不记录来自哪个策略版本 | 无法分析策略变更对数据质量的影响 |

**根因总结**：
1. **评测指标设计缺陷**：指标 incentivize 错误行为（做完 ≠ 做好，快 ≠ 好）
2. **数据质量失控**：训练数据标签噪声大，坏数据污染模型
3. **评测与迭代脱节**：评测结果无法指导具体的策略改进方向

---

## 第二步：提出假设

> **假设**：如果重建评测体系——(1) 从"完成导向"转为"意图对齐导向"的多维评测；(2) 建立数据质量管道（自动标注 + 人工校验 + 质量分级）；(3) 将评测结果与策略迭代闭环（每个 badcase 映射到具体策略规则）——则评测指标将与用户满意度重新对齐，后训练数据质量将显著提升，模型与框架的迭代将形成正向循环。

---

## 第三步：设计策略规则

设计的评测体系与后训练数据策略规则（对应 QwenPaw 的 `observability/` + `governance/` + `tool_calls/` + `agents/memory/` + `loop/gates/`）：

```
评测体系与后训练数据策略 v1：

=== 评测指标重构（Evaluation Metrics Redesign）===

规则 E1：多维评测框架
  废弃单一"任务完成率"，替换为 5 维评测：

  维度 1 — 意图对齐度（Intent Alignment）：
    - 检查 Agent 的输出是否覆盖了用户指令中的所有要求
    - 自动化：LLM-as-Judge 对比用户指令 vs Agent 输出
    - 评分：0-5 分（0=完全偏离，5=完全对齐）
    - 例：用户说"替换所有 console.log，不要跳过任何目录"
         Agent 跳过了 tests/ → 意图对齐度 = 3（部分对齐）

  维度 2 — 完成质量（Completion Quality）：
    - 检查 Agent 输出的质量（代码能否运行？文件是否正确？）
    - 自动化：执行验证（代码编译/测试通过/文件存在）
    - 评分：0-5 分（0=不可用，5=完全可用）

  维度 3 — 效率（Efficiency）：
    - 不仅看轮次，还看"有效轮次占比"
    - 有效轮次 = 产生实质性进展的轮次
    - 无效轮次 = 重试/报错/偏离主题的轮次
    - 效率分 = 有效轮次 / 总轮次

  维度 4 — 安全性（Safety）：
    - 检查 Agent 是否有危险行为（删除文件、执行危险命令、泄露敏感信息）
    - 自动化：governance 审计日志分析
    - 评分：0-5 分（0=有危险行为，5=完全安全）

  维度 5 — 用户体验（User Experience）：
    - 用户满意度（/👎）+ 用户介入率 + 用户重复率
    - 用户介入率 = 用户不得不手动纠正 Agent 的比例
    - 用户重复率 = 用户不得不重复之前说过的话的比例

  综合得分 = 加权平均（意图对齐 30% + 完成质量 30% + 效率 15% + 安全性 15% + 用户体验 10%）

规则 E2：评测集分层
  将评测集按难度分层，避免"简单任务拉高平均分"：

  Level 1 — 简单任务（单步骤，明确指令）：
    · "写一个 hello world 函数"
    · 权重：10%

  Level 2 — 中等任务（2-3 步骤，有约束条件）：
    · "写一个排序函数，要求时间复杂度 O(n log n)"
    · 权重：30%

  Level 3 — 复杂任务（4+ 步骤，跨领域）：
    · "添加用户认证功能：API + UI + 路由守卫 + 测试"
    · 权重：40%

  Level 4 — 长程任务（跨 session，需要记忆）：
    · "继续昨天的合同起草，把争议解决条款写详细"
    · 权重：20%

  报告时分难度层级展示，避免平均分掩盖问题

规则 E3：Badcase 自动分类
  每个失败任务自动归类到策略课题：

  分类体系：
  - CONTEXT: 上下文压缩/分层问题
  - MEMORY: 记忆写入/召回/失效问题
  - TOOL: 工具选择/执行/编排问题
  - PLANNING: 任务规划/收敛/Subagent 问题
  - SAFETY: 安全/权限/治理问题
  - COMMUNICATION: 理解偏差/意图对齐问题

  自动分类方法：
  1. 分析事件流中的错误模式
  2. 匹配预定义的 badcase 模式库
  3. LLM-as-Judge 辅助分类（对模糊案例）
  4. 输出：badcase → 策略课题 → 具体规则编号

=== 后训练数据管道（Post-training Data Pipeline）===

规则 D1：数据质量分级
  废弃二元"成功/失败"标签，改为 4 级质量：

  Grade A — 高质量数据（可直接用于训练）：
    · 意图对齐度 ≥ 4
    · 完成质量 ≥ 4
    · 用户明确 👍 且有正面文字反馈
    · 无安全警告
    · 占比目标：20%

  Grade B — 中等质量数据（需修正后使用）：
    · 意图对齐度 ≥ 3
    · 完成质量 ≥ 3
    · 用户 👍 但无文字反馈
    · 有小问题但不影响核心功能
    · 占比目标：40%

  Grade C — 低质量数据（仅用于负例训练）：
    · 意图对齐度 < 3 或 完成质量 < 3
    · 用户 👎 或无反馈
    · 有明显问题
    · 用途：DPO 负例、错误模式学习
    · 占比目标：30%

  Grade D — 废弃数据（不进入训练集）：
    · 有安全事件
    · 数据损坏/不完整
    · 标注矛盾
    · 占比目标：< 10%

规则 D2：自动标注 + 人工校验
  数据标注流程：

  阶段 1 — 自动标注（LLM-as-Judge）：
    · 对每个 session 自动计算 5 维评分
    · 自动分类 badcase
    · 自动分配质量等级
    · 成本：$0.01/session

  阶段 2 — 抽样人工校验：
    · Grade A 数据：100% 人工校验（确保训练集质量）
    · Grade B 数据：30% 人工校验
    · Grade C 数据：10% 人工校验（验证负例质量）
    · Grade D 数据：不校验（直接废弃）
    · 人工校验员标注与自动标注的一致性 > 85% → 自动标注可信

  阶段 3 — 争议仲裁：
    · 自动标注与人工标注不一致 → 高级标注员仲裁
    · 仲裁结果反馈到自动标注模型（持续改进）

规则 D3：数据版本追溯
  每条训练数据记录完整元数据：

  {
    "data_id": "session_8823",
    "quality_grade": "B",
    "strategy_version": "v4.2.1",
    "model_version": "qwen-max-2024-03",
    "evaluation_scores": {
      "intent_alignment": 4,
      "completion_quality": 4,
      "efficiency": 3,
      "safety": 5,
      "user_experience": 4
    },
    "badcase_categories": [],
    "annotation_method": "auto+human_verified",
    "annotator_id": "judge_v2.1",
    "timestamp": "2024-03-15T10:30:00"
  }

  用途：
  - 分析哪个策略版本产生的数据质量最高
  - 追踪数据质量随时间的变化趋势
  - 回滚问题时定位到具体策略版本

规则 D4：合成数据生产
  从 badcase 自动生成训练数据：

  流程：
  1. 收集 badcase（意图对齐度 < 3 的任务）
  2. 分析 badcase 根因（自动分类）
  3. 生成"修正版"对话：
     · 保留用户原始指令
     · 用正确的策略重新生成 Agent 回复
     · 标注"这是修正后的正确行为"
  4. 修正版数据作为 SFT 正例
  5. 原始 badcase 作为 DPO 负例

  质量控制：
  - 合成数据必须经过人工校验（Grade A 标准）
  - 合成数据占比不超过训练集的 30%
  - 合成数据与真实数据分开评估效果

=== 评测-迭代闭环（Evaluation-Iteration Loop）===

规则 I1：策略规则映射
  每个 badcase 自动映射到具体策略规则：

  例：
  badcase: "Agent 跳过了 tests/ 目录的 console.log 替换"
    → 分类: TOOL (工具执行范围判断错误)
    → 映射规则: 工具与 Skill 编排 → O1 (Skill 级工具白名单)
    → 建议改进: 扩展工具范围判断逻辑，不要自行决定跳过目录

  月度报告：
  | 策略课题 | badcase 数量 | 占比 | Top 3 规则 |
  |---------|------------|------|-----------|
  | TOOL | 45 | 30% | O1, S1, S3 |
  | MEMORY | 35 | 23% | R1, R2, W1 |
  | PLANNING | 30 | 20% | F1, P1, C3 |
  | CONTEXT | 25 | 17% | L0, L2 |
  | SAFETY | 15 | 10% | G1, G2 |

规则 I2：A/B 实验标准化
  每个策略改进必须经过标准化 A/B 实验：

  实验模板：
  {
    "experiment_id": "EXP-2024-03-001",
    "hypothesis": "扩展工具范围判断逻辑可降低跳过文件的 badcase",
    "strategy_change": "修改 file_search 工具的范围判断规则",
    "control_group": "当前策略 v5.0",
    "treatment_group": "新策略 v5.1",
    "metrics": ["intent_alignment", "completion_quality", ...],
    "sample_size": 200,
    "success_criteria": "intent_alignment 提升 ≥ 5pp",
    "duration": "7 days"
  }

规则 I3：模型-框架协同迭代
  评测结果同时指导模型和框架的改进：

  框架侧改进（策略规则调整）：
    · badcase 分类为 CONTEXT/MEMORY/TOOL/PLANNING → 调整对应策略规则
    · 效果立竿见影（不需要重新训练模型）

  模型侧改进（后训练数据）：
    · badcase 分类为 COMMUNICATION（理解偏差）→ 补充 SFT/DPO 数据
    · 效果需要重新训练模型（周期长，但解决根本问题）

  协同原则：
    · 框架能解决的问题 → 优先改框架（快）
    · 框架解决不了的问题 → 改模型（慢但根本）
    · 两者同步迭代，不互相等待
```

## 第四步：设计实验验证

设计了 A/B 实验，使用 500 个历史任务（覆盖 4 个难度层级）回测：

| 维度 | 对照组（当前体系） | 实验组 v1 |
|------|-----------------|----------|
| 评测指标 | 3 维（完成率/轮次/工具准确率） | 5 维（意图对齐/质量/效率/安全/体验） |
| 评测集 | 混合难度，不分层 | 4 层难度分层 |
| 数据标签 | 二元（成功/失败） | 4 级质量分级 |
| 数据标注 | 人工 100% | 自动标注 + 抽样人工校验 |
| Badcase 分类 | 无 | 自动分类到 6 个策略课题 |
| 合成数据 | 无 | 从 badcase 自动生成修正版 |

**评测指标**：

```python
metrics = {
    # 评测体系质量
    "metric_user_satisfaction_correlation": 评测指标与用户满意度的相关性,
    "evaluation_coverage": 评测覆盖的场景比例,
    "badcase_classification_accuracy": badcase 自动分类准确率,

    # 数据质量
    "data_label_accuracy": 数据标签准确率（vs 人工标注）,
    "grade_a_data_proportion": Grade A 数据占比,
    "synthetic_data_quality_score": 合成数据质量评分,

    # 迭代效率
    "strategy_rule_mapping_accuracy": 策略规则映射准确率,
    "experiment_cycle_time": A/B 实验周期（从假设到结论）,
    "framework_vs_model_fix_ratio": 框架修复 vs 模型修复的比例,

    # 业务指标
    "user_satisfaction_nps": 用户 NPS,
    "user_complaint_rate": 用户投诉率,
    "model_performance_after_retrain": 重新训练后的模型性能提升,
}
```

## 第五步：实验结果与迭代

**v1 实验结果**（500 个历史任务回测 + 2 周线上 A/B）：

| 指标 | 对照组 | 实验组 v1 | 变化 |
|------|-------|----------|------|
| 指标-满意度相关性 | 0.23 | 0.78 | +0.55 ✅ |
| 数据标签准确率 | 62% | 89% | +27pp ✅ |
| Grade A 数据占比 | N/A | 22% | 达标 ✅ |
| Badcase 分类准确率 | N/A | 81% | ✅ |
| 合成数据质量评分 | N/A | 4.1/5 | ✅ |
| 策略规则映射准确率 | N/A | 76% | ✅ |
| A/B 实验周期 | 14 天 | 7 天 | -50% ✅ |
| 用户 NPS（线上 A/B） | 12 | 28 | +16 ✅ |
| 用户投诉率（线上 A/B） | 8.5% | 4.2% | -4.3pp ✅ |
| **新问题：LLM-as-Judge 偏差** | N/A | **出现** | **❌** |

**归因 v1 的新问题**：LLM-as-Judge 在"意图对齐度"评分上存在系统性偏差——对"Agent 做了很多工作"的任务倾向于给高分（努力偏见），对"Agent 做得少但精准"的任务倾向于给低分。导致效率高的 Agent 反而被低评。

## 第六步：策略迭代 v2

调整规则：

```
v2 改进：

评测指标增强：
- E1 增加"努力偏见"校正：
  · 意图对齐度评分时，LLM-as-Judge 的 prompt 中明确说明：
    "评分基于结果是否满足用户意图，而非 Agent 做了多少工作。
     一个精准完成所有要求的简短回复应得 5 分，
     一个做了大量工作但遗漏关键要求的回复应得低分。"
  · 引入"校准集"：100 个人工标注的 golden sample
  · 每月用校准集检测 LLM-as-Judge 的偏差，动态调整 prompt

- E3 增加"跨版本对比"：
  · badcase 分类结果按策略版本分组
  · 对比相邻版本的 badcase 分布变化
  · 如果某策略课题的 badcase 占比上升 → 告警（新策略引入回归）

数据管道增强：
- D2 增加"标注一致性监控"：
  · 每周计算自动标注与人工标注的一致性
  · 一致性 < 80% → 触发标注模型重新校准
  · 记录不一致的案例类型（哪些类型的 badcase 最难自动标注）

- D4 增加"合成数据去重"：
  · 合成数据与已有训练集做语义去重
  · 避免合成数据与真实数据高度重复（降低训练效率）
  · 去重阈值：语义相似度 > 0.9 视为重复

迭代闭环增强：
- I3 增加"框架-模型优先级矩阵"：
  | 问题类型 | 框架修复 | 模型修复 | 优先级 |
  |---------|---------|---------|-------|
  | 工具误选 | ✅ 改工具描述/排序 | ❌ | 框架优先 |
  | 上下文压缩丢失 | ✅ 改分层策略 | ❌ | 框架优先 |
  | 记忆召回失败 | ✅ 改召回策略 | ❌ | 框架优先 |
  | 理解偏差 | ❌ | ✅ SFT/DPO | 模型优先 |
  | 推理能力不足 | ❌ | ✅ 持续预训练 | 模型优先 |

```

## 案例总结：评测体系与后训练数据的核心洞察

| 洞察 | 说明 |
|------|------|
| **指标会 incentivize 行为** | "完成率" incentivize 假完成，"轮次少" incentivize 偷懒——指标设计就是策略设计 |
| **用户 👍 不是可靠信号** | 用户反馈噪声太大，需要多维自动标注 + 抽样人工校验 |
| **评测必须与满意度对齐** | 指标涨但 NPS 跌 = 指标设计失败，必须重建 |
| **Badcase 分类是迭代加速器** | 自动分类到策略课题 → 直接定位改进方向，无需人工分析 |
| **框架修复优先于模型修复** | 72% 的问题可以通过策略规则调整解决，不需要等模型重训 |
| **合成数据有价值但需控制** | 从 badcase 生成修正版数据是高效的数据增强，但需去重和质量控制 |
| **LLM-as-Judge 需要校准** | 自动标注有系统性偏差（努力偏见），需要 golden sample 持续校准 |
| **数据版本追溯是回滚基础** | 记录每条数据的策略版本，才能在出问题时定位和回滚 |
