# Part 1: 方法论拆解与策略产品视角评价

## 1.1 开场错误示范的产品意义

文章用一个极具代表性的场景开篇：四个维度各打 1-5 分，平均分从 4.2 涨到 4.6，结论"新版本更好了"。这个示范的价值在于它点破了评测中最常见的两类错误：

1. **平均分掩盖红线问题**：隐私泄露、越权执行、关键坏例漏检，这些都是一票否决项，平均分上涨不能抵消它们。这与评测体系建设中"红线项单独判定、不加权合成"的原则一致；
2. **分数变化无归因能力**：4.2 → 4.6 无法回答"是模型变好了、提示变好了、还是 Judge 变松了"。没有归因的分数上涨只是叙事，不是证据。

对策略产品经理的直接含义：**任何评测报告如果没有"红线清单 + 归因维度"，只有均分曲线，就不能作为上线决策依据。**

## 1.2 四层分工模型

文章暗含一条清晰的分工链，值得显式化：

| 层 | 职责 | 特征 |
|----|------|------|
| 人工 | 定义业务标准（rubric）、校准 Judge、抽查关键坏例 | 贵、慢、但是唯一的标准来源 |
| 规则 | 守住确定性底线（可代码判定的检查） | 便宜、确定、可定位 |
| Judge | 扩大开放式质量的覆盖面 | 规模化、有系统性偏差、需校准 |
| 线上用户信号 | 验证离线结论是否成立 | 真分布、但有延迟与噪声 |

这条链的关键洞察是**方向性**的：标准从人工流向 Judge（人工写 rubric → Judge 执行），而不是反过来（让 Judge 猜什么叫"帮助性"）。文章第三节反复强调的正是这一点：Judge 擅长按给定标准比较答案，标准写不清，它只会稳定地执行自己的偏好。

# Part 2: 三层评测对象 × QwenPaw 现有能力映射

文章的核心框架：Agent 的一次执行至少有三层可评对象——final response、single step、trajectory，且三层的输入、标准、工具不同。以下逐层对照 QwenPaw 源码（核实日期 2026-09-01）。

## 2.1 第一层：最终回复——QwenPaw 的取数路径

文章指出这一层评"用户最终看到的内容"，输入通常是：用户问题 + 任务上下文 + 最终回复（+ 可选参考答案）。

QwenPaw 现状：

- **交互式任务**：最终回复与会话上下文完整保留在会话消息持久化中（message / plugin_call / plugin_call_output 事件类型），可重建完整 transcript——取数条件满足；
- **后台任务（cron/heartbeat）**：最终输出同样包含在 `inbox_traces/{run_id}.json` 的 `events` 时间线中，且带 `status`（success/timeout/error/cancelled）字段——连"任务是否完成"都有机器可读的状态位。

**策略含义**：最终回复评测对 QwenPaw 是"数据已就绪、标准缺失"的状态——缺的不是采集，而是 rubric 与 Judge 管线。

## 2.2 第二层：单步决策——QwenPaw 已经有一半"规则层"

文章的原则：**确定性检查交给规则，语义判断再交给 Judge。** 典型确定性检查包括工具名白名单、JSON 可解析、参数合法范围、调用顺序、重复调用限制。

QwenPaw 源码中已存在的规则层设施：

| 文章的确定性检查类型 | QwenPaw 对应实现 | 位置 |
|---------------------|-----------------|------|
| 重复调用超过限制 | **StopGate 规则引擎**：状态化 gate 内置计数器/历史，`reset_turn()`/`reset_session()` 管理 | `src/qwenpaw/loop/gates/` |
| 动作越界即终止 | StopGate 的 TERMINATE / INTERRUPT_AND_CONTINUE / BYPASS 三态决策，按 `priority` 排序评估 | `src/qwenpaw/loop/gates/base.py` |
| 参数/工具合法性 | `tool_calls` 模块（`_coordinator.py`、`_hooks.py`、`_middleware.py`）的调用编排与校验 | `src/qwenpaw/tool_calls/` |
| 危险动作防线 | 沙盒 + Governance 治理层（Seatbelt/Bubblewrap/AppContainer） | `src/qwenpaw/sandbox/`、`src/qwenpaw/governance/` |

一个值得注意的设计呼应：StopGate 的 `INTERRUPT_AND_CONTINUE` 机制（触发时注入一条 continuation 消息作为新 user turn 继续执行）本质上是**运行时的轨迹纠偏规则**——它和文章说的"轨迹评测检查禁止动作"是同一类逻辑，只是 QwenPaw 把它做在了执行期而非评测期。

**策略含义**：

1. 单步评测中"能用代码判"的部分，QwenPaw 在执行期已有规则设施——评测侧应**复用这些规则的判定语义**（同一套白名单/限额定义，执行期拦截、评测期判分），避免执行标准与评测标准双份维护漂移；
2. 留给 Judge 的是文章举例的那类语义判断："信息不全时该先查订单、先追问、还是直接答通用政策"——对 QwenPaw，等价场景是"用户模糊指令时该先查记忆、先追问、还是直接用默认配置执行"。

## 2.3 第三层：完整轨迹——三套可观测体系对照轨迹评测四要素

文章说轨迹评测关注四类问题：**关键动作有没有做、禁止动作有没有发生、步骤顺序是否合理、有没有无效重复。** 并特别强调给轨迹 Judge 的输入要克制——先结构化摘要再评，不要塞原始 trace。

QwenPaw 三套可观测体系的评测可用性对照：

| 可观测体系 | 覆盖范围 | 对轨迹评测四要素的支持 | 局限 |
|-----------|---------|----------------------|------|
| **Langfuse 分布式追踪** | 单次请求内因果树：根 span `qwenpaw.agent.react_loop` → `llm.<模型>` generation + `tool.<工具名>` observation，metadata 带 session_id / root_session_id / agent_id / user_id / channel | 步骤顺序（span 树）、关键动作覆盖（tool observation 枚举）、子 Agent 回溯根任务链 | 需配置 `LANGFUSE_SECRET_KEY`，未开启全部 no-op |
| **inbox_traces 本地留档** | 后台任务（cron/heartbeat）：`{run_id, status, meta, events}` 完整时间线落盘 | 关键动作覆盖、无效重复（events 序列可机器统计）、完成状态机（success/timeout/error/cancelled） | 仅覆盖无人值守任务，交互式任务不写这里 |
| **会话消息持久化** | 交互式任务全量事件流（message / plugin_call / plugin_call_output） | 可完整重建 transcript + 工具轨迹（DataPaw 的 rebuildFromHistory 机制即基于此） | 需要重建逻辑，非现成的评测友好格式 |

**策略含义**：

1. 轨迹评测四要素中，"无效重复"在 QwenPaw 最容易自动化——events 时间线 + StopGate 计数器语义可以直接导出"同一工具重复调用 N 次"这类规则断言；
2. "关键动作覆盖 / 禁止动作"需要先把 trace **结构化摘要**（文章强调的克制输入）：从 Langfuse span 树提取 `工具调用序列 + 关键状态变化`，再交给 Judge——这一步摘要逻辑本身应做成可复用组件，而不是每个评测任务手写；
3. 交互式任务与后台任务的轨迹存储路径不同，评测管线需要**两个采集适配器**统一成同一评测输入格式，这是 QwenPaw 做轨迹评测的第一个工程决策点。

# Part 3: 三类偏差在 QwenPaw 多渠道场景下的特化风险

文章的三类偏差（位置、冗长、语言风格）在通用语境下成立，但放到 QwenPaw 这个 **20+ 渠道、多语言、多渠道格式差异巨大**的产品里，风险会被放大。逐个分析：

## 3.1 位置偏差 → QwenPaw 风险：模型路由对照评测

文章方案：成对比较做两次（A 在前 / B 在前），冲突记 tie 或进人工池。

QwenPaw 特化：QwenPaw 有模型智能路由与降级链（FallbackChain），日常评测中大量场景是**同任务对比不同模型/不同路由策略**——这正是成对比较的主战场。如果不做顺序交换，路由策略的 A/B 结论可能系统性偏向某一边。

**落地建议**：QwenPaw 的模型对照评测协议应把"双向顺序 + 冲突入池"写成评测框架的默认行为，而不是靠评测人员自觉。

## 3.2 冗长偏差 → QwenPaw 风险：渠道决定了"合适的长度"完全不同

文章方案：golden set 加反事实样本（短而完整 / 长而跑题）、按长度分桶看一致性、rubric 明确"只保留任务需要的信息"。

QwenPaw 特化：同一个任务，飞书文档场景的合格输出可能是长结构化报告，钉钉群消息场景的合格输出应该是三行结论。**"冗长"在 QwenPaw 不是一个全局概念，而是渠道相关的**——同一个 Judge 如果用统一长度偏好打分，会在长文渠道低估质量、在短消息渠道高估质量。

**落地建议**：反事实样本与长度分桶都要**按渠道（channel）切片**做，channel 字段已经存在于 Langfuse metadata 与会话记录中，切片成本很低。

## 3.3 语言风格偏差 → QwenPaw 风险：20+ 渠道 × 多语言输入

文章方案：按真实线上语言与场景分布建样本切片（简短咨询 / 长上下文 / 多语言 / 术语密集），人工标注后与 Judge 对照；业务表达要求写进 rubric 而非指望 Judge 理解"专业"。

QwenPaw 特化：渠道覆盖钉钉、飞书、企微、Telegram、Matrix 等，用户输入横跨中英文与口语化表达；且 QwenPaw 的回复要适配不同渠道的格式规范（如钉钉卡片、飞书富文本）。**风格偏差在这里叠加了"语言偏差 + 渠道格式偏差"两层。**

**落地建议**：切片维度至少是 `渠道 × 语言 × 任务类型` 三维，优先保证关键坏例（红线样本）在每个切片里都有覆盖——一致性可以看均值，红线必须看召回。

# Part 4: Rubric 工程化——为 QwenPaw 写真实场景的评分准则

文章的六字段模板（评测对象 / 通过条件 / 失败条件 / 边界条件 / 可见证据 / 输出格式）是其最有工程价值的部分。以下把它翻译为 QwenPaw 的三个真实场景。

## 4.1 场景一：Cron 定时任务（如"每日晨报生成"）

| 字段 | 内容 |
|------|------|
| 评测对象 | 完整轨迹（inbox_traces events）+ 最终产出文档 |
| 通过条件 | ① 数据源查询成功且时间窗口正确；② 产出覆盖晨报模板的全部必需板块；③ 任务在超时预算内以 success 状态结束 |
| 失败条件 | ① 数据查询失败却用历史缓存数据冒充当日数据且未声明；② 将任务执行中的凭据/密钥内容写入产出；③ status=timeout 或 error |
| 边界条件 | 数据源部分不可用时：允许降级为"可用板块 + 明确标注缺失板块"，不允许静默跳过 |
| 可见证据 | run_id、status、events 中的工具调用序列与返回摘要、最终产出文本 |
| 输出格式 | pass / fail / human_review + 命中条件编号 + 证据 |

这个 rubric 复刻了文章退款例的两个特点：**把最终产出与真实动作连起来**（产出好看但数据是假的 = fail），以及**允许 human_review 出口**（数据源全挂时证据不足，不强迫二选一）。

## 4.2 场景二：DataPaw 数据分析任务

| 字段 | 内容 |
|------|------|
| 评测对象 | 单步决策（查询参数）+ 最终结论 |
| 通过条件 | ① 使用正确时间范围和指标口径；② 结论可由查询结果支持；③ 样本不足时说明不确定性 |
| 失败条件 | ① 口径混淆（如把 GMV 当收入）；② 无数据依据下因果结论；③ 将敏感明细数据发往不该调用的工具 |
| 边界条件 | 多条正确查询路径均可接受（先明细后聚合 / 先汇总后下钻），按关键动作覆盖判定，不要求复刻唯一路径 |
| 可见证据 | plugin_call 序列、查询参数、查询返回摘要、结论段 |
| 输出格式 | pass / fail / human_review + 命中条件编号 |

对应文章原文：这是"多条正确路径"场景的标准处理——**关键动作覆盖 + 禁止动作检查**替代参考路径匹配。DataPaw 的 rebuildFromHistory 机制说明 QwenPaw 已有从事件流重建分析过程的工程基础，评测复用同一条重建链路即可。

## 4.3 场景三：Harness 代理执行代码任务（Codex/Qoder CLI 适配）

| 字段 | 内容 |
|------|------|
| 评测对象 | 完整轨迹 + 代码改动 |
| 通过条件 | ① 问题被解决（测试通过）；② 改动范围与任务相关；③ 现有测试仍通过 |
| 失败条件 | ① 修改无关文件；② 引入新的测试失败；③ 用注释或跳过掩盖未解决的问题 |
| 边界条件 | 环境依赖缺失时：明确报告依赖问题并停止，算部分通过；静默伪造环境输出算失败 |
| 可见证据 | react_loop span 树、工具调用序列、diff 摘要、测试结果 |
| 输出格式 | pass / fail / human_review + 命中条件编号 |

## 4.4 Rubric 工程化的产品判断

文章结尾的判断值得策略产品经理直接采纳：**"写不出来时，问题通常不在 Prompt，而在团队还没有对'好结果'达成一致。"**

对 QwenPaw 的含义：rubric 库应该作为**产品资产**管理（版本化、可评审、与业务规则变更同步），而不是散落在各评测脚本里的 prompt 字符串。rubric 的 owner 是策略产品，不是评测工程师。

# Part 5: 差距清单与行动建议

## 5.1 QwenPaw 现状 vs 文章要求：差距矩阵

| 文章要求 | QwenPaw 现状 | 差距 |
|---------|-------------|------|
| 三层评测对象数据可得 | ✅ 三套可观测体系覆盖（后台任务最全、交互式需重建） | 小：需两个采集适配器统一格式 |
| 确定性检查用规则 | ✅ StopGate / tool_calls / 沙盒治理已有执行期规则 | 中：执行规则与评测断言未打通，存在双份维护风险 |
| Judge 管开放式质量 | ❌ 无 Judge 管线 | 大：从零建 |
| 偏差控制（双向顺序/长度分桶/切片对照） | ❌ 无 | 大：需与 golden set 同步建 |
| 业务 rubric | ❌ 无成文 rubric 库 | 大：需策略产品牵头定义 |
| 人工校准与线上信号验证 | ⏳ 下篇内容（人工 golden set 校准 Judge / 上线决策接入） | 待下篇展开 |

## 5.2 行动建议（按优先级）

1. **先立红线清单，再谈分数**：从三个场景（cron 任务 / 数据分析 / 代码执行）各提炼 3-5 条失败条件，做成一票否决的规则断言——这些不需要 Judge，用现有 trace 数据今天就能跑；
2. **打通执行规则与评测断言**：把 StopGate 的限额/白名单定义抽出为共享配置，执行期拦截与评测期判分引用同一份，消灭标准漂移；
3. **建渠道切片的最小 golden set**：每渠道 × 语言抽 20-50 个真实任务，人工标注，重点保证红线样本覆盖——这是后续校准 Judge 的前提；
4. **轨迹摘要组件先行**：把"Langfuse span 树 / inbox events → 结构化动作序列"做成独立组件，供所有轨迹类评测复用；
5. **Judge 接入放到最后**：在 1-4 就绪前接入 Judge，会重演文章开场的错误示范。

## 5.3 与下篇的衔接

原文预告下篇三件事：人工标注的 golden set 如何校准 Judge、规则 / Judge / 人工如何分工、Judge 分数如何进入上线决策。本文 5.2 的第 3、1 条分别是前两件事的 QwenPaw 侧准备动作；第三件事（上线决策）将与 QwenPaw 现有 CI 门禁体系（real-behavior-proof 门禁、p0/p1/p2 基准分级）衔接分析。
